- 직전 단계: `TEX02-R009`
- 근거 우선순위: **사용자가 GitHub에 올린 Minecraft Java 1.21.11 추출본** `1.21.11/`의 blockstate JSON과 컴파일된 Java 클래스 직접 열람
- 공식 Mojang client.jar SHA-1/manifest 인증은 완료 기준에서 제외하며, 인증 성공을 주장하지 않음
- **실제 Minecraft 게임 렌더링 실행이나 정적 인게임 스크린샷 검증은 이번에도 0/17**

## 새로 확인한 핵심 사실

이전 R009에서는 17개 blockstate JSON의 총 31개 변형 선언 중 `uvlock` 명시가 0건이라는 **JSON 사실**만 알고 있었다. R010에서는 **실제 클라이언트의 JSON 디코딩 → 모델 상태 생성 → UV 행렬 선택 경로**를 별도로 추적했다. 따라서 '키가 없는 경우 엔진이 기본적으로 무엇을 택하는가'를 원본 코드 근거로 답할 수 있게 됐다.

1. **`hqq$a.class`** (`Variant.SimpleModelState` 역할): `MapCodec`에서 `x/y/z` 세 축을 읽고, `Codec.BOOL.optionalFieldOf("uvlock", false)`에 해당하는 분기를 갖는다. 원본 상수 풀에서 `"uvlock"`과 `optionalFieldOf`를 확인했고 그 앞에는 `iconst_0`가 들어 있다. 클래스의 기본 상태 객체 또한 세 축의 기본 회전과 `false` 플래그로 생성된다.
2. **`hqq$a.a():Lioc;`**: 원본 35바이트 메서드에서 `f.a(x,y,z) → inm.a(f)` (일반 회전 상태)를 만들고, 보관된 `uvlock` boolean이 **true일 때에만** `inm.b()`로 UV 잠금 구현체를 선택한다. false이면 그대로 일반 `inm` 반환.
3. **`inm.class`**: `ioc` 인터페이스를 직접 구현하고 위치 변환을 반환한다. 방향별 `ioc.a(Direction)` / `ioc.b(Direction)`를 재정의하지 않는다. `inm.b():Lioc;`는 `inm$a` 인스턴스를 반환하며, 이는 위 2번 분기에서 true일 때 선택된다.
4. **`inm$a.class`**: `ioc`를 구현한 별도 UV 잠금 경로. 방향별 `a(Direction)`는 부모 `inm.f`의 면 행렬, `b(Direction)`는 부모 `inm.g`의 역면 행렬을 맵에서 가져온다. 이는 일반 상태와 실제 차이가 있는 조건부 경로다.
5. **`ioc.class`**: 인터페이스의 `a(Direction)`와 `b(Direction)` 기본 구현은 공용 `Matrix4f()`를 반환한다. 클래스 초기화에서 항등행렬을 만든다. `hqi.class`의 `bakeQuad`는 앞선 R009에서 확인한 대로 `ioc.b(Direction)` 경로를 사용한다.
6. **`hqq.class`**: 모델 bake 진입 지점에서 자신이 보관한 `hqq$a`의 `a():Lioc;`를 호출해 결과를 bake 루틴에 전달한다. 독립적인 타입 추측만으로 연결한 것이 아니라, 실제 클래스 호출 경로가 확인된다.

## 31개 선언에 적용한 정적 코드 경로 결과

`EFFECTIVE_UVLOCK_31_VARIANTS.csv`는 17개 JSON을 **이번 R010에서도 직접 다시 읽어**, 기존 31개 상태별로 다음 항목을 새로 연결해 작성한 결과다.

- **JSON에 `uvlock` 키를 쓴 상태: 0/31**.
- **`hqq$a`의 기본값으로 복원된 `uvlock=false` 상태: 31/31**.
- **선택되는 모델 상태의 코드상 경로: 일반 `inm` 31/31, UV 잠금 `inm$a` 0/31**.
- **일반 `inm` 경로에서 `ioc.b(Direction)`로 반환되는 UV 보정 행렬: 항등행렬 31/31**.
- 선언에 등장하는 회전 튜플은 `(x,y,z)` **5종**: `(0,0,0)` 19건, `(0,180,0)` 4건, `(90,90,0)` 4건, `(90,0,0)` 2건, `(90,180,0)` 2건. 모든 `z=0`.
- 개별 31개 목록은 `model`, `axis` property, variant index, Git blob SHA까지 기록. 이것은 기존 31개 블록상태 선언의 **새로운 속성/코드 경로 연결 분석**이지 새로운 블록상태 31개 발견으로 계산하지 않는다.

여기서 **항등행렬**이 의미하는 것은 `FaceBakery`의 해당 UV *잠금 보정 변환*이 정상 분기에서 UV 좌표를 추가로 회전시키지 않는다는 것이다. **모델의 정점 위치 회전은 계속 일어난다.** 반면 **면 재정렬, 텍스처 좌표의 시각적 방향, 최종 baked quad, GPU 출력·조명·랜덤 선택을 모두 해결했다는 뜻은 아니다**.

## 소스와 추론의 구분

**원본 클래스 직접 확인:** `hqq$a`의 optional UVLOCK false, `hqq$a.a()` 분기, `inm`/ `inm$a` 각각의 인터페이스 메서드, `ioc` 기본 행렬, `hqq`의 bake 연결. `CLASS_SOURCE_SHA_LEDGER.csv`에 클래스 6개를 기록. 이 중 **R010에 신규로 연 클래스 4개**는 `hqq$a`, `hqq`, `inm`, `inm$a`; `ioc`, `hqi`는 이전 단계 근거 재사용이다. 15개의 source/bytecode 코드 경로와 교차근거를 `UVLOCK_CLASS_BYTECODE_CHAIN.csv`에 정리했다.

**모델 추론:** 31개의 JSON 값에 코드상 디코딩 규칙을 대입하면 `uvlock=false`와 항등 UV 보정 경로가 된다. **실제 게임을 실행해 31개 상태가 런타임에 선택되는 과정을 계측한 결과는 아니다.** 이를 '모델 상태 생성 알고리즘으로 도출한 경로'로 표시했다.

**불확실:** `f.a(x,y,z)`의 실제 3축 회전 행렬 수치와 `hqi`의 면 재배열까지 연쇄 적용한 **완전한 각 면의 게임 baked quad 정점/UV 숫자**, R007의 134개 이음새의 실제 대응, 텍스처 필터·광원·랜덤 선택 확률, 인게임 스크린샷. 이번 소스 확인만으로 A–G 완료 처리하지 않는다.
