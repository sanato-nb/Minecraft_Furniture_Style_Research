# v28 — 바닐라 문·다락문·울타리 문·계단 104개 상태 규칙과 참나무 문 40면 원본 UV 실화소

- 연구일: **2026-11-13 KST**
- 기준: 사용자 제공 GitHub `1.21.11/assets/minecraft/`; 기존 v27 바닐라 연구에서 이어지는 **상위 1단계 01 텍스처 / 02 3D·상태·UV** 연구.
- 이 단계는 사용자가 업로드한 JSON 및 PNG의 **직접 원본 판독·픽셀 측정**이다. Mojang 정식 `client.jar` 독립 획득/검증이나 실제 게임 런타임 검증은 수행하지 않았다.
- 모드 연구 v24 누적 지표 변경 없음. 게임 원본 자산은 새 연구 산출물에 복제하지 않고 파생 CSV·Git blob SHA/보고서만 게시.

## 1. 블록 상태 4개 원본의 104 variants 전체 읽기

`blockstates/oak_door.json`, `oak_trapdoor.json`, `oak_fence_gate.json`, `oak_stairs.json`를 GitHub 원본에서 직접 읽고 `variants` 모든 항목을 다음 [01 전수 104항목 CSV](01_four_blockstates_104_exact_variants.csv)에 기록했다. 키별 `facing`, `half`, `hinge`, `shape`, `in_wall`, `open`, 모델 경로, `x/y` 회전, `uvlock` 지정 여부를 분리하여 저장했다.

| 대상 | 원본 variants | 서로 다른 참조 모델 경로 | `uvlock:true` 명시 | 비0 `x` | 비0 `y` |
|---|---:|---:|---:|---:|---:|
| 참나무 문 `oak_door` | 32 | 8 | 0 | 0 | 24 |
| 참나무 다락문 `oak_trapdoor` | 16 | 3 | 0 | 0 | 6 |
| 참나무 울타리 문 `oak_fence_gate` | 16 | 4 | 16 | 0 | 12 |
| 참나무 계단 `oak_stairs` | 40 | 3 | 35 | 20 | 30 |
| **합계** | **104** | **18 고유 경로** | **51** | **20** | **72** |

**엄밀한 주의:** `uvlock:true` 51항목은 원본에 `true`가 *명시된 항목* 수다. 나머지 **53항목은 모두 키 자체가 없는 것**으로 확인했고, 소스에서 `uvlock:false`가 명시됐다고 바꿔 쓰지 않는다. `y=0`은 키가 없으면 통계에서 0으로 기록한 *기본값 통합 표기*로, 소스에 반드시 `y:0`이 적힌 것은 아니다. 이 값과 실제 렌더된 UV 회전 결과는 별개다. `oak_stairs`의 `x:180`은 윗면 20개 조합에 기재된다.

### 네 유형의 구조적 차이

- **문:** `facing 4 × half lower/upper 2 × hinge left/right 2 × open true/false 2 = 32`개 상태를 **8개 leaf 모델과 회전 값**으로 매핑. 하나의 문은 상·하 2블록으로 분리돼 있지만, CSV의 32행을 **동일 위치에서 32개 모델을 동시에 적용한 것**으로 보면 안 된다.
- **다락문:** `facing 4 × half 2 × open 2 = 16`항목을 **bottom/top/open 세 모델**로 매핑. 기존 v26 다락문 원본 UV 실측은 반복하지 않았다.
- **울타리 문:** `facing 4 × in_wall 2 × open 2 = 16`항목을 **평상/열림/담장 연결/담장 연결+열림 4종**의 모델로 대응시키며 모든 항목에 `uvlock:true` 명시.
- **계단:** `facing 4 × half 2 × shape 5 = 40`항목에 `x/y` 회전과 `uvlock` 여부가 함께 등장. 기존 v25/27 샘플 모델의 UV 생성식과 이 블록 상태 *회전 후 UV*는 같은 검증 대상이 아니다.

## 2. 참나무 문 leaf 8종 ↔ 부모 8종 직접 연결

[04 원본 leaf 8종 경로·부모·Git SHA](04_oak_door_8_leaf_parent_geometry_sha.csv)와 [03 부모 8종 면 UV 원본 이미지 픽셀](03_oak_door_eight_templates_40_faces_uv_rgba.csv) 참조.

- 참나무 문 `oak_door_bottom_left`, `..._right`, `..._open`, `..._top_...` 등 **8개 leaf**는 각각 `door_bottom_left` 등의 **8개 서로 다른 부모 템플릿**을 참조한다. **8 leaf 자체 요소는 모두 0개**, 각 부모 템플릿은 자체 요소 **1개**, 명시 face **5개**를 가진다.
- 부모 8종 각 요소의 원시 좌표는 **`from=[0,0,0]`, `to=[3,16,16]`로 동일**하며, 열린 모델의 UV 반전 및 면별 UV 사각형 선택이 다르다. 출처는 **source JSON**이다. 회전 적용 후 실제 인게임 외형 좌표는 아니다.
- 8개 부모의 선언 face는 합산 **40면**이다. 하단 부모는 `#bottom`에서 `oak_door_bottom`, 상단 부모는 `#top`에서 `oak_door_top` 이미지를 참조하는 방식으로 직접 확인.

## 3. 참나무 문 원본 PNG 2종 전체 RGBA 및 40면 UV 해석

기존 v4의 150표본에 들어 있는 `oak_door_bottom.png`, `oak_door_top.png`를 이번 v28에서 **사용자 업로드 원본 바이너리로 다시 직접 전체 픽셀 디코딩**했다. 이번 첫 검사가 아니라 **기존 표본 원본 재검증**이며 새 텍스처 누적 종류에 추가하면 안 된다.

| 원본 이미지 | 크기 | 고유 RGBA | 완전 불투명 | 완전 투명 | 부분 투명 |
|---|---:|---:|---:|---:|---:|
| `oak_door_bottom` | 16×16 | 9 | 256 | 0 | 0 |
| `oak_door_top` | 16×16 | 11(투명 RGBA 포함) | 208 | 48 | 0 |
| **소스 이미지 2종 총계** | **512픽셀** | 색상종류 합산 금지 | **464** | **48** | **0** |

[02 원본 PNG 두 종 전 화소 통계](02_oak_door_two_png_full_rgba.csv)

- 원본 8개 부모의 `faces.*.uv`를 **40면 전부 직접 판독**해서 해당 원본 PNG 영역의 RGB/알파 픽셀을 샘플. 결과 **40 face × 선언 UV 사각형에서 총 5,248회 텍셀 참조**: **불투명 4,864회, 완전 투명 384회, 부분 투명 0회**. `uv` 반전 선언 **21/40면**, 0면적 face 0.
- 하단 모델 4종 각 면의 이미지 참조 면적 합은 **656 texel-uses**이며 전부 불투명. 상단 4종도 각각 656 texel-uses이지만 전면과 뒷면의 16×16 사각형에 **각 48개 투명 픽셀**이 포함되어, 상단 **96회 투명 픽셀 사용/템플릿**이 나온다. 이것은 여러 부모와 양면/면 반복을 포함한 횟수로, 개별 PNG의 48투명 픽셀이 8배로 많아진 것이 아니다.
- v4 `01_누적150종_픽셀측정.csv`와의 **2/2** 원본 파일 바이트 길이, 16×16 크기, 픽셀 총수, 가시 픽셀 수 일치. v4 `unique_rgb_visible`(가시 RGB 색 수)와 v28 `unique_rgba`(투명 영역도 포함한 RGBA 조합 수)를 혼동하지 말 것. `oak_door_top`의 경우 각각 **10 vs 11**로 지표 정의가 다르다. v4 SHA-256을 이번에 독립 재계산한 것은 아님.
- 비공식 공개 `InventivetalentDev/minecraft-assets` 1.21.11 추출본과 원본 PNG Git blob SHA **2/2 정확 일치**. **이것은 공식 Mojang 배포 client.jar 검증이 아니다**.

## 4. 참나무 울타리 문: 문과 다른 방식으로 상태별 형상 변경

참나무 울타리 문 모델 leaf 4개와 원형 템플릿 4개를 실제 사용자 저장소 JSON에서 읽어 [05 상속·기하·Git SHA CSV](05_oak_fence_gate_4_templates_4_leaf_geometry.csv)에 저장했다.

| 템플릿 | 자체 요소 | 명시 faces | 원시 bbox X/Y/Z |
|---|---:|---:|---|
| `template_fence_gate` | 8 | 40 | [0,5,7]–[16,16,9] |
| `template_fence_gate_open` | 8 | 40 | [0,5,7]–[16,16,15] |
| `template_fence_gate_wall` | 8 | 40 | [0,2,7]–[16,13,9] |

- 모델 원형 4개는 각각 **8요소·40면 선언**, 합계 **32개 독립 원형 요소 선언/160면 선언**. 실제로 월드에 울타리 문 4개가 동시에 렌더됐다는 뜻이 아니다.
- **open** 템플릿은 z 최대가 9→15로, **in_wall** 템플릿은 Y 범위가 [5,16]→[2,13]으로 바뀐다. 곧 다른 방향·담장 연결 상태에서는 단지 모델을 돌리는 것뿐 아니라 실제 **부품 좌표가 다른 원형**을 선택한다는 사실이 JSON에서 확인된다.
- 참나무 울타리 문 leaf 4개는 모두 자체 요소 0개, 해당 템플릿 상속 및 `minecraft:block/oak_planks` 텍스처 참조. **oak_planks PNG는 v26에서 이미 실화소 디코딩**했으므로 이번에 신규 화소로 중복 추가하지 않았다.
- 모델 원형 160면의 각 `oak_planks` PNG 내부 UV 실제 픽셀 전체 검사는 **이번 범위 밖**이다. 여기서는 기하와 blockstate 정의까지만 직접 검증했다.

## 5. 이번 체크포인트 누적 경계와 다음 순서

- **신규 원본 상태 정의/선정 분석 확대:** 4개 blockstate의 **104 variants 전체 원본**, 이 중 `oak_door/oak_trapdoor/oak_stairs`의 JSON 파일은 v25 또는 이전 단계의 일부 샘플에서 읽은 적이 있어 **104개를 프로젝트 처음 읽은 상태라고 합산하지 않는다**. 새로 추가한 것은 *기존보다 자세한 104개 각 행의 구조·회전·UVlock 증거표*와 `oak_fence_gate` 상태 및 원형 기하 비교다.
- **v28 PNG 전 화소 재검사 2경로/512픽셀**. 2개 모두 기존 v4 표본이며 **신규 고유 텍스처 0종**. 그러나 새로 연결한 문 부모 8종의 **고유 명시 face 40면·5,248 texel-uses**는 v26/27의 선정 면 연구와 별개다.
- `uvlock:true` 플래그 자체의 사용은 검증했지만, **클라이언트 내부 UV 보정 수학식/실제 게임에서 텍스처가 어떻게 보이는지는 검증하지 않았다**. 방위별 회전값 0·90·180·270도는 source 속성값 그대로 기록. 각 상태의 충돌체/조명/애니메이션/렌더 결과는 이번 범위 밖.
- v24 기존 Another Furniture 선택 leaf 204, blockstate 22/177, 두 모드 PNG175/면 RGBA4,113은 **변동 없음**.
- 상위 1단계 **01 표본 150/150**, 02 바닐라 구조·UV 보완 **진행 중**, 03/04 모드 연구 **보존**, 05 최종 비교 **미완료**. **최종 판정 완료 0/5**, 임의의 전체 연구 진행률 %는 계산하지 않는다.
- **다음 우선 순서:** (1) 독립적으로 확보한 공식 Mojang 1.21.11 `client.jar` 출처·SHA 비교 (2) `uvlock` + x/y rotation 실제 로더/렌더 적용의 검증 (3) 울타리 문 160면 등 미조사 바닐라 면의 실제 PNG UV 검사와 추가 가구형 블록 (4) 인게임 시각·조명·연결 상태 비교 (5) 바닐라·모드 스타일 비교 단계 착수.
