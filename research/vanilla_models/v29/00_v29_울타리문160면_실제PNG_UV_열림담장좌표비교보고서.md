## 1. v28 미완료 160면을 원본 PNG에 실제 대조

v28에 JSON 선언으로만 확인하고 **텍셀 픽셀을 읽지 않았던** 네 원형:
`template_fence_gate`, `template_fence_gate_open`, `template_fence_gate_wall`, `template_fence_gate_wall_open`.

- 사용자 업로드 저장소의 원본 JSON 네 파일을 다시 열어, 원본 **Git blob SHA**와 `elements` 8개/템플릿, `faces` 40개/템플릿을 확인했다.
- **4템플릿×40면 = 160개 source declared face**의 `faces.*.uv`를 직접 추출. **160/160 명시된 UV**이고, UV 범위 0–16의 **정수 좌표**만 사용(암시적 UV 0). 전체 **0면적 UV 0**, 역방향 UV 0, 모든 면은 `#texture` 슬롯을 참조한다.
- 해당 4 leaf `oak_fence_gate*`는 `#texture`를 **`minecraft:block/oak_planks`**로 묶는 것을 v28 원본에서 확인했다. `oak_planks.png`는 기존 v26에서 분석된 **16×16/7가지 RGB 색/256 완전 불투명** 텍스처이므로 신규 PNG 경로로 계수하지 않는다.
- 이번에는 GitHub에서 `oak_planks.png` **195바이트를 직접 재취득**하고 Python/Pillow로 PNG 자체를 열어 `verify()` 후 모든 RGBA 픽셀을 해독했다. 재계산한 **Git blob SHA `e5a15780171bdff340a8bab625c31d0891e8ba5e`**가 원본 GitHub SHA와 일치했다. 별도로 **SHA-256 `65665943ef9c8bcf63fc67d2083ed0c50243f724106d0e4bb1abea5d921b16d3`**을 독립 재계산하여 기존 v4 150종 표본 CSV의 해당 해시와 **완전 일치**를 확인했다. 이 검사는 **PNG 1장만**에 대한 독립 파일·픽셀 교차검사다.
- 원본 PNG에서 독립 디코딩한 16×16 픽셀을 각 JSON face `uv`의 사각형 범위에 연결해 **160면 모두 원본 RGBA 1,952 텍셀 참조**를 계산했다. 총 참조 **불투명 1,952 / 완전 투명 0 / 부분 알파 0**. **1,952는 중복을 포함한 face별 사용 수**, 1,952개의 서로 다른 소스 픽셀 또는 게임 화면 픽셀 수가 아니다.

## 2. 실제 모델 요소 차이: 열린 위치 6개 / 담장 연결 시 정확한 y -3

네 원본 템플릿의 **8개 요소를 동일 인덱스로 대응**시켜, `from/to` 좌표를 정수 단위로 비교한 [06 기하 변경 CSV](06_eight_element_open_wall_geometry_deltas.csv)를 작성했다.

- **일반 → 열림:** 두 기둥(`element 0,1`)은 from/to 좌표가 변하지 않는다(**2/8 동일**). 나머지 **6/8 요소**는 x/z 위치 또는 x/z 범위가 변하며, **y 좌표는 전 요소에서 불변**이다. 즉, 문짝·연결부의 좌표만 바뀌고 두 지지기둥은 자리를 지키는 원본 구성이다. 닫힌 원형 bbox는 **[0,5,7]–[16,16,9]**, 열린 원형 bbox는 **[0,5,7]–[16,16,15]**다.
- **일반 → 담장 연결:** 8개 요소 **전부** `from.y`와 `to.y`가 **정확히 -3**, x/z 값 변화 **0**. 즉 `[0,5,7]–[16,16,9]` → **[0,2,7]–[16,13,9]**.
- **열림 → 담장 연결+열림:** 같은 y **-3** 변환이 **8/8 요소에서 정확히 동일**하게 적용된다. 열린 bbox **[0,5,7]–[16,16,15]** → 담장 연결+열림 bbox **[0,2,7]–[16,13,15]**.
- 이는 사전 배치된 **네 가지 source model의 요소 좌표를 비교해 얻은 정적인 법칙**이다. 게임이 각 요소를 실시간 모션으로 보간/애니메이션한다고 입증한 것이 아니다. 실제 인게임 회전·충돌체·바운딩/조명은 별도 검증이 필요하다.

## 3. 블록 상태 16종과 기하 원형 및 UV 소스 연결

원본 `blockstates/oak_fence_gate.json`의 `facing 4 × open 2 × in_wall 2 = 16` 조합을 직접 재파싱했다. **각 상태는 정확히 4종 중 1개 원형 leaf**를 참조하며 각 원형은 **4개 방향**에서 선택된다.

- 모든 **16/16** 상태는 `uvlock:true`를 **명시**한다.
- `y` 회전 값은 원본에 기록된 0/90/180/270을 보존했다. 이 CSV의 `rotation_y`는 **JSON 소스 속성**이며 각 면의 인게임 최종 UV 결과나 방향 변환 시뮬레이션이 아니다.
- 각 상태는 실질적으로 원형 8요소·40선언면의 구조를 선택하므로 `16×40=640`은 *상태별 적용 인스턴스 합*이지 **새 원본 face 640개 발견**을 뜻하지 않는다. v29 실제 신규 고유 UV 원본 face 분석은 **160개**뿐이다.

## 4. 무엇을 새로 학습했고 아직 미확인인가

**직접 확인할 수 있는 가구 모델링 관찰**
1. 하나의 바닐라 가구형 구조는 **4개의 서로 다른 완성형 모델 원형**과 상태의 모델 선택만으로 열림·벽 연결·방향 변화를 표현한다.
2. **8요소 중 2개 기둥은 유지/6개 부품만 재배치**되는 열림 사례를 관찰했다. 단순 정육면체 모델을 무작정 다시 조합하는 것보다 상태별 움직이는 부분을 구조적으로 분리할 수 있다는 유용한 설계 근거다.
3. `in_wall`은 다른 모양을 처음부터 만들기보다 **원시 요소 전체를 y축 -3 이동한 동일 구조**로 표현하며, **열림과 담장 연결의 차이를 별개 축**으로 다루고 있음을 원본 8/8 델타 일치로 검증했다.
4. 원본 면 UV는 **열림에 따라 픽셀 사각형 재배치**되며 40면의 텍셀 참조 합계는 닫힘 512/열림 464로 차이가 난다. 이 숫자는 단순 화소 빈도이지 면별 화면 면적·렌더링 품질의 직접 비교가 아니다.

**검증하지 않은 것**
- 독립적으로 인증된 Mojang 공식 `client.jar` 내용 및 전체 업로드 자료 진위.
- 실제 `uvlock` 알고리즘과 x/y 회전, 컬링, 음영, 투명 레이어, 충돌체, 게임 스크린샷.
- `oak_planks` 외 다른 텍스처에 대한 Pillow 독립 재검사(이번에 검사한 건 **1종**).
- 공개 저장소의 게임 원본 `.class`·PNG·JSON 재배포 권한. 새 연구 파일에 원본 이미지를 복제하지 않았고, 공개 배포 위험은 계속 별도 검토 필요.
