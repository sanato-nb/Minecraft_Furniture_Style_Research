## **1. 프로젝트의 최종 목적**

\*\*Minecraft Furniture Style Research\*\*의 목적은 Minecraft 바닐라와 여러 가구 모드를 연구하여, **AI가 Minecraft 스타일의 새로운 가구 모델을 정확하게 만들 수 있도록 재사용 가능한 지식을 축적하는 것**이야.

단순히 모델 JSON과 PNG를 수집하는 데서 끝나는 연구가 아니야.

| 목표     | 확정 내용                                  |
| ------ | -------------------------------------- |
| 연구 대상  | Minecraft Java Edition 바닐라 및 다양한 가구 모드 |
| 핵심 연구  | 3D 모델 구조, 텍스처, UV, 블록상태, 스타일           |
| 디자인 연구 | 부품 구성, 상대 비율, 형태·색상·질감 특징              |
| 지식 구축  | AI가 재사용할 수 있는 모델링 기법과 근거               |
| 향후 활용  | AI가 Blockbench 호환 모델·텍스처·블록상태 생성       |
| 상위 목표  | 프로젝트 좀보이드 → 마인크래프트 맵 제작                |
| 현재 제외  | 실제 좀보이드 맵 변환, 가구 제작 본 작업               |

**연구 자체가 독립적인 프로젝트**이고, 좀보이드 맵 변환은 나중의 활용 목적이야.

**② Minecraft 가구 모드**

의자·책상·테이블·수납장 등 각 모드의 관련 가구를 연구. 모드는 하나씩 독립된 연구 단위로 취급.

확정한 세부 정책은 다음과 같아.

- **Minecraft 버전 하나로 전체 연구를 고정하지 않음.** 연구 대상마다 정확한 버전을 기록.
- **Forge·Fabric 등 특정 로더만 고집하지 않음.** 모델 구조가 주요 연구 대상이므로 필요한 로더 정보를 출처와 함께 기록.
- **바닐라를 먼저 연구한 다음 가구 모드를 개별적으로 연구.**
- **연구 대상으로 정한 원본은 전수 열거.** 임의의 몇 개 모델만 분석하고 전체 연구 완료로 처리하지 않음.
- 모드가 업데이트되면 새로 추가되거나 변경된 부분부터 증분 연구. 삭제된 리소스와 그 영향도 기록.
- 사용자가 원하면 기존 연구 전체를 처음부터 다시 검증하는 방식도 지원.

연구 회차 모드는 기존 저장소의 네 가지를 유지해.

| 모드            | 목적                |
| ------------- | ----------------- |
| `NEW`         | 신규 대상 연구          |
| `INCREMENTAL` | 두 버전 간 변경분 연구     |
| `REVALIDATE`  | 기존 연구 결과 재검증      |
| `FRESH`       | 지정 범위를 처음부터 다시 연구 |

## **3. 연구 시작 전 반드시 거쳐야 하는 3단계**

이 부분은 연구가 끝없이 늘어나는 것을 막기 위해 가장 중요하게 확정한 규칙이야.

1. **원본 사전 조사**

   실제 파일, 버전, 경로, 파일 형식, 모델 수, 텍스처 수, 블록상태, 상속·참조 관계와 지원 여부 조사.

   전체 대상의 정확한 분모를 확인.
2. **연구 범위 상세 확정**

   포함·제외 대상, 필수 검사, 렌더링 조건, 근거 기준, 미지원 처리, 실패 조건과 종료 기준을 사전에 문서화.
3. **실행계획 상세 확정**

   작업 순서, 입력·출력, 검증 방법, 환경, 체크포인트, 결과 저장, 완료 판정을 미리 지정.

**범위·계획 고정 후 실제 연구 시작**

### **연구 중 새로운 의문이 생기면?**

확정된 규칙은 다음과 같아.

1. 발견한 문제와 새로운 연구 아이디어를 별도 기록한다.
2. 기존 연구 범위를 임의로 늘리지 않는다.
3. 원래 계획한 연구와 종료 심사를 먼저 완료한다.
4. 그다음 후속 연구 후보를 한 번에 정리해 제안한다.
5. 사용자 승인 후 별도의 연구로 시작한다.

단, **기존 고정 범위 안에서 발견한 실제 분석 오류는 수정하고 재검증해야 해.** 새로운 연구 과제를 추가하는 것과는 구분하는 거야.

의자의 각 구성 요소가 어떤 형태로 조립되는지, 다리·좌판·등받이의 상대 비율이 어떤지, 텍스처와 UV가 어떤 디자인 효과를 만드는지까지 연구해야 해.

## **5. 연구 결과의 정확성 정책**

모든 데이터를 같은 확실성으로 취급하지 않아.

| 근거 상태            | 의미            |
| ---------------- | ------------- |
| `SOURCE`         | 원본에서 직접 확인    |
| `CALCULATED`     | 원본 값으로 계산     |
| `OBSERVED`       | 이미지 등에서 직접 관찰 |
| `INFERRED`       | 근거를 바탕으로 추론   |
| `UNKNOWN`        | 판단 불가능        |
| `NOT_APPLICABLE` | 해당 사항 없음      |

의자의 좌판이라고 추정한 부품도 실제로는 다른 역할을 할 수 있어.

따라서 다음을 분리하기로 했어.

**객관적인 구조 정보**

- 좌표, 치수, 회전, UV, PNG 해상도, 모델 참조 등
- 원본과 계산 근거가 확인되면 확정 가능

**의미적·디자인 정보**

- 의자 다리인지, 장식인지, 제작 의도가 무엇인지 등
- 확정·추정·미확인으로 신뢰도를 구분

### **연구 완료 상태**

| 상태      | 판정 기준                 |
| ------- | --------------------- |
| PASS    | 고정된 필수 검증 전부 통과       |
| PARTIAL | 일부 범위만 검증 완료          |
| HOLD    | 실행 환경·원본 문제 등으로 판단 불가 |
| FAIL    | 필수 검증 실패              |

**검사 시도 수와 검증 성공 수는 분리해서 관리한다**는 것도 확정했어.

예를 들어 모델 1,000개 중 950개를 정상 검증했다면, 1,000개를 조사했다는 기록과 950개가 검증됐다는 기록을 모두 남겨야 해. 전체를 100% 완료라고 표시하지 않아.

## **6. 데이터베이스 및 결과 저장 정책**

**SQLite를 연구 데이터의 기준 저장소로 사용하고, JSON과 Markdown을 출력용으로 생성**하는 방향으로 정했어.

**SQLite — 단일 기준 데이터**

**JSON**

AI 검색·도구 연동

**Markdown**

사람이 읽는 연구 보고서

SQLite 안에서는 다음 여섯 계층으로 정보를 관리하는 개념을 잡았어.

| 계층        | 역할                  |
| --------- | ------------------- |
| 1. 원본 색인  | 버전, 파일, 경로, 해시, 출처  |
| 2. 원본 구조  | 모델·요소·면·텍스처·상태      |
| 3. 계산 결과  | 크기, 비율, UV, 통계      |
| 4. 모델링 지식 | 디자인 원칙·부품 역할·기법     |
| 5. 검증 기록  | 테스트, 실패, 근거, 미해결    |
| 6. 연구 운영  | 범위, 작업 상태, 후속 연구 후보 |

### **확정된 DB 운영 원칙**

- 같은 원본 정보를 여러 곳에 불필요하게 중복 저장하지 않음
- 데이터마다 출처·버전·원본 식별자 연결
- 객관 구조와 AI 추론을 분리
- 검증 범위와 미검증 범위를 분리
- 다른 연구에서도 데이터를 검색·재사용할 수 있도록 구성
- 기존 역사 DB 및 원본은 보존
- 라이선스를 확인하지 않은 제3자 모델·텍스처를 재배포하지 않음

**아직 미완료인 것:** 14개 데이터 영역의 실제 물리적 SQLite 테이블 설계와 기존 운영 DB 연결 방식은 최종 확정되지 않았어.

### **렌더링 실행 방식**

기존에 우려했던 모델마다 Blender를 실행하고 종료하는 방식을 사용하지 않아.

```
GitHub Actions 시작
       │
       ▼
Python 원본 분석
       │
       ▼
Blender 실행 (1회)
       │
       ├── 모델 1 렌더링
       ├── 모델 2 렌더링
       ├── 모델 3 렌더링
       └── 모델 N 렌더링
       │
       ▼
검증 결과·체크포인트 저장
       │
       ▼
Blender 종료
```

Job마다 렌더러가 종료되는 건 허용하고, 다음 Job에서 미완료 작업을 이어서 수행하는 구조를 목표로 해.

다만 **현재 성공한 것은 하나의 GitHub Actions Job 안에서 Blender 프로세스를 재시작하고 재개하는 방식**이야. 서로 다른 Job 사이에서 체크포인트를 복원하는 기능까지 검증한 것은 아니야.

### **왜 웹 직접 조작을 제외했나?**

대량 연구에서는 AI가 모델 하나씩 웹사이트를 열어 확인하는 방식보다, 프로그램이 자동 분석하고 AI가 중요한 예외를 검수하는 방식이 더 효율적일 것으로 판단했기 때문이야.

이전에 제시했던 토큰 차이 15배는 가상 계산일 뿐 실제 측정값은 아니야.

**연구 철학:** 단순한 모델 파일 수집이 아니라 AI가 재사용할 수 있는 객관적인 구조 정보와 상세 디자인 지식을 축적한다.

**연구 범위:** 바닐라부터 시작해 다양한 가구 모드를 하나씩 독립적으로, 사전에 정한 범위 안에서 전수 연구한다.

**작업환경:** Python + Blender + GitHub Actions + SQLite를 중심으로 하고, Blockbench 웹 직접 조작과 유료 AI API는 기본 과정에서 제외한다.
