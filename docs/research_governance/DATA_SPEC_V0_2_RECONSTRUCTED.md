# Minecraft Furniture Style Research — 데이터 명세 v0.2 (합의사항 재구성본)

> **문서 성격:** 첨부된 전체 합의 정리본과 기존 대화에서 확정한 14개 연구 영역을 분야별로 재구성한 문서. 이전 v0.2 원문을 1:1 복사한 문서는 아니다.
>
> **상태:** 데이터 내용·근거·보존 원칙 합의. **물리적인 SQLite 테이블 구성, 마이그레이션과 최종 컬럼명은 아직 확정되지 않음.** 아래 개념을 구현 완료로 표시하지 않는다.

## 1. 최종 데이터 사용 목적

Minecraft Java 바닐라와 가구 모드의 원본에서 **정확한 구조 데이터와 디자인·모델링 기법 지식**을 수집하여, 이후 AI가 블록 모델 JSON·텍스처 PNG·면별 UV·블록상태 JSON을 제작할 때 근거를 조회할 수 있도록 한다.

단순히 원본 JSON을 보관하는 것이 목표가 아니다. 어떤 가구의 어떤 부분이 어떤 비율·형태·기법으로 구성되는지를 재사용할 수 있어야 한다.

## 2. 데이터 저장 원칙

- **SQLite**: 연구의 기준 데이터 저장소(single source of truth).
- **JSON**: AI 검색, 프로그램 간 전달, 분석 결과 내보내기.
- **Markdown**: 사람이 읽는 보고서와 근거 요약.
- 데이터별 출처 원본, 연구 대상·버전, 경로, 해시, 분석 범위, 계산·해석 유형, 검증 상태에 연결한다.
- 중복 저장은 줄이고 개별 기록을 원본/모델/텍스처/상태/연구 회차 식별자로 연결한다.
- 이미 존재하는 기존 SQLite 카탈로그 및 과거 증거는 수정·삭제하기 전에 품질 조사와 연결 설계를 진행한다.
- 원본 파일 자체의 저장·배포 여부와 분석 수치·지식의 저장을 구분하고 제3자 라이선스 제한을 준수한다.

## 3. 여섯 개 개념 계층

| 계층 | 역할 | 핵심 연결 |
|---|---|---|
| 1. 원본 색인 | 연구 대상·버전·릴리스·파일·경로·해시·참조 관계 | 원본 식별자 |
| 2. 원본 구조 | 모델·요소·면·텍스처·UV·블록상태 원본값 | 원본 모델/리소스 |
| 3. 계산 결과 | 크기·비율·회전 결과·색상·패턴·통계 | 계산 근거와 알고리즘 |
| 4. 모델링 지식 | 부품 역할, 디자인 원칙, 제작 순서, 적용 조건 | 원본 사례와 신뢰도 |
| 5. 검증 기록 | 정적 검사·렌더링·기대값·실패·미지원 | 연구 회차·검증 항목 |
| 6. 연구 운영 | 사전 조사·잠긴 범위·계획·체크포인트·진행도·후속 과제 | 연구 ID/범위 버전 |

이 분류는 **개념 모델**이며 각 계층을 반드시 단일 테이블로 만든다는 뜻이 아니다.

## 4. 반드시 다루는 데이터 영역 14개

| 번호 | 영역 | 요구되는 지식 범위 |
|---:|---|---|
| 1 | 연구 대상·버전·출처 | Minecraft/모드 이름, 원본·Minecraft 버전, 로더, 배포·고정 근거 |
| 2 | 원본 파일 색인 | 경로, 자산 형식, 해시·크기, 중복·누락·지원 여부, 참조 관계 |
| 3 | 모델 기본 구조 | 모델 파일 종류, `parent`, 요소 수, 원본 변환·상속 |
| 4 | 3D 요소·형상 | `from`/`to`, 치수, 원점, 회전, 요소 조립·면 구성 |
| 5 | 면별 UV | face, 텍스처 별칭·실제 해석 결과, UV 좌표·회전, `cullface` |
| 6 | 텍스처·픽셀 스타일 | PNG 크기, 알파·투명도, 색상, 대비, 픽셀 패턴, 추정 재질 |
| 7 | 블록상태 | `variants`/`multipart`, 상태값, 방향, 회전·변환 및 적용 대상 |
| 8 | 모델·텍스처·상태 참조 그래프 | 부모, 참조 대상, 순환·누락, 네임스페이스와 해석 결과 |
| 9 | 오프라인 렌더링 | 적용 환경, 카메라, 출력 이미지, 해시, 로그, 성공·실패·비교 결과 |
| 10 | 가구 종류·부품 의미 | 기능적 분류, 다리·좌판·등받이 등 부품 역할 및 신뢰도 |
| 11 | 형태·비율·스타일 | 상대 치수, 대칭·복잡도, 장식, 색·재질 스타일, 바닐라와 모드 비교 |
| 12 | 재사용 가능한 제작 기법 | 단계별 조립 기법, 적용 조건·한계, 소스 사례와 신뢰도 |
| 13 | 검증·예외·완료 | 검사별 판정, 시도·검증 수, 오류·미지원, PARTIAL/HOLD/FAIL |
| 14 | AI용 지식 검색 색인 | 종류·부품·비율·색·스타일·제작법·출처·근거 기반 검색 |

### 4.1 객관적인 구조와 의미적 해석의 분리

- 구조 기록: 좌표, 회전, 요소 수, 면별 UV, 이미지 해상도, 파일 해시 등은 원본 또는 계산 근거를 사용한다.
- 해석 기록: '손잡이', '다리', '좌판', '등받이', '장식' 등은 확인 수준을 나누어 기록한다.
- 부품 정체가 `UNKNOWN`이더라도 확인된 좌표·크기·면 정보를 삭제하거나 실패 처리하지 않는다.
- 제작 기법의 일반화는 다양한 사례의 근거를 요구하며 단일 소스의 주장을 전체 가구 유형으로 확대하지 않는다.

### 4.2 지식 활용 예시

의자 연구의 목표는 '요소 8개' 같은 숫자뿐만이 아니라, **다리와 좌판 높이의 관계, 등받이의 구성, 텍스처 재사용 방법, UV 방향, 모델 복잡도**를 근거와 함께 질의할 수 있게 하는 것이다.

이 지식은 이후 다른 스타일의 새로운 모델을 제작할 때 참고할 수 있지만, 현재 단계에서 실제 생성 성공을 완료 조건으로 요구하지 않는다.

## 5. 증거 분류

| 분류 | 용도 |
|---|---|
| `SOURCE` | 원본 파일에서 직접 읽은 사실 |
| `CALCULATED` | 원본값 및 명시된 계산으로 얻은 결과 |
| `OBSERVED` | 이미지·렌더 결과 등에서 관찰한 사실 |
| `INFERRED` | 근거를 바탕으로 추론한 모델링·의미 정보 |
| `UNKNOWN` | 현재 근거로 판단 불가 |
| `NOT_APPLICABLE` | 해당되지 않음 |

각 결과의 근거 출처를 추적할 수 있도록 연결한다. 의미적 부품 분류는 확정·추정·미확인을 명시한다.

## 6. 범위와 진행률을 위한 기록

연구별로 아래 수치를 혼합하지 않는다.

- 원본 사전 조사에서 확정한 **대상 전체 수**
- 실제 분석·렌더·검증을 **시도한 수**
- 정해진 독립 검증을 **통과한 수**
- 미지원·미확인·실패·보류 항목 수
- 대상별 검증된 범위와 미검증 범위

| 완료 판정 | 데이터에서 표현할 사실 |
|---|---|
| `PASS` | 잠긴 필수 조건 전부 통과 |
| `PARTIAL` | 검증 완료 부분만 인정 |
| `HOLD` | 필수 항목 판단 불가 |
| `FAIL` | 명시된 검증 실패 |

**추가 주의:** 렌더링 PNG 생성 성공 기록과 원본 Minecraft 형상·UV·상태에 대한 정확성 기록은 별도 필드/검증 상태로 관리해야 한다.

## 7. 기존 저장소와 연결 시 주의점

현재 GitHub의 `src/mcfr/research_db.py` 등 기존 SQLite 기반 카탈로그가 이미 존재한다. 따라서 새 14개 영역을 구현할 때 기존 버전·자산·연구 회차 원장을 확인하고 **중복 테이블을 먼저 만드는 방식은 피한다.**

기존 자료는 다음으로 품질 분류한 뒤 재사용 범위를 결정한다.

- 재사용 가능
- 재검증 필요
- 역사 참고용
- 중복·불필요 후보(임의 삭제 금지)

## 8. TV-001 연결 및 미완료

- [TV-001 고정 계약](../tech_validation/TV001_SCOPE_AND_EXECUTION_V1_1.md)은 12개 입력·25개 렌더링의 **기술 검증**이다.
- 이미지 25개와 기본 검사의 CI 성공이 확인됐더라도, 독립 형상·UV·회전·상태 정확성을 검증하지 않은 범위는 **미완료**이다.
- TV-001 테스트용 체크포인트·임시 데이터는 기존 운영 연구 DB와 분리한다.

### 아직 확정하지 않은 구현 상세

이 문서에서는 실제 SQL DDL, 테이블 수·이름, PK/FK 물리 설계, 마이그레이션 스크립트, 데이터 통합 완료 여부, 전체 대상의 행 수를 새로 확정하지 않는다. 이 항목은 **기존 GitHub 자료 품질 조사와 연구 DB 상세 설계**에서 결정한다.
