# 1-1 재질 연구 — 새 채팅 분리 및 고유 버전 운영 규칙

> 2026-11-13 설정. **이 문서는 버전/인수인계 인프라를 만드는 작업이며 신규 PNG 검증 완료를 뜻하지 않는다.** 바닐라 1.21.11 정적 재질·텍스처 연구용.

## 버전 충돌 방지 — 기존 `v38`과 별개의 이름 공간

- 과거 전체 연구 통합 버전 `v1`~`v38`은 기존 파일·인수인계에만 사용. **1-1 개별 재질 연구에 `v39`, `v40`, `v32` 등 단독 `v숫자`를 절대 쓰지 않는다.**
- 각 단계의 고유 접두어는 **`1-1-01`→`TEX01`**, `1-1-02`→`TEX02`, ... `1-1-11`→`TEX11`. 
- `TEX01-R000`, `TEX02-R000`, ..., `TEX11-R000`은 각 단계의 **최초 계획/인수인계 스냅샷**. 이 계획 스냅샷이 A–G 검사를 실제로 끝냈다는 뜻이 아니다.
- **실제 신규 검증이 발생할 때만** 단계별 `TEXnn-R001`을 만들고 그 단계 내에서 `R002`, `R003` ...로 증가. 즉 `TEX01-R001`과 `TEX02-R001`은 서로 다른 고유 버전이고 전체 `v38`과도 겹치지 않는다.
- 앞으로 실행 결과 경로는 `research/vanilla_textures/by_stage/1-1-nn/TEXnn-R001/`처럼 **절대 경로를 나눠 쓰는 불변 원장**. 기존 릴리스를 덮어쓰지 않고 다음 릴리스 폴더를 만든다.
- 각 채팅은 **본인 단계의** `docs/vanilla_texture_1-1/stages/1-1-nn/STATE.json`, `HANDOFF.md`만 변경한다. 다른 단계의 문서와 루트 `HANDOFF.md`, `PROGRESS.md`, `handoff/STATE.json`은 절대로 수정하지 않는다. 전체 통합 통계/체크포인트 갱신은 별도 통합 작업에서만 수행.
- **같은 단계를 여러 채팅에서 동시에 쓰기 금지**. 같은 단계 병행을 반드시 해야 한다면 새 브랜치/서로 다른 작업자 식별자를 선할당하고 통합 시 겹침 검사. 일반적으로 `STATE.json` 현재 SHA와 `current_revision`을 매 작업 직전에 다시 읽어, 동일 `next_revision`이 이미 있으면 다른 번호를 새로 잡는다. GitHub의 SHA 낙관적 갱신으로 다른 채팅 쓰기를 덮어쓰지 않는다.
- 저장 전에 Github repo owner, 단계 번호, 고유 출력 버전, 파일 존재 여부 확인; 신규 릴리스에 `REPORT.md`, `SOURCE_LEDGER.csv`, `SUMMARY.json`과 원본 파일/커밋 출처를 남긴다. 실데이터를 확보하지 못한 경우 `pending`을 기록하고 **임의 완료·가공 측정·버전 증가 금지**.

## 동일한 단계에서 새 채팅 시작 절차

1. [11개 독립 채팅 링크/작업 번호](README.md)에서 단계를 골라 **그 단계의 `START_PROMPT.md` 내용을 새 채팅에 붙여넣는다.**
2. 새 채팅은 GitHub 연결을 통해 **반드시** 해당 단계의 `HANDOFF.md`, `STATE.json`, 기존 1-1 번호별 대상 목록을 다시 확인하고, 자신의 마지막 `TEXnn-Rxxx`부터 이어간다.
3. `A→G`: 기존 기록 대조 → 원본 SHA/픽셀 확인 → 색상·반복·알파 → 재질 특화 → 모델/UV 정적 검증 → 공식 JAR·인게임 정적 검증 → 파일 저장/증거 감사. **애니메이션 연구 보류**, 기존의 동적 기록 보존.
4. 체크 기준은 **파일별/검증수준별**(기존 측정, 이번 직접 검증, 공식 원본 인증, 인게임 정적 렌더). 단순 텍스처 파일 수 150/150을 전체 완료율로 표시하면 안 된다.
5. 연구 범위는 바닐라 재질 분석으로, **Project Zomboid 변환·실제 가구 모델 제작은 하지 않는다**. 공식 Minecraft 1.21.11 `client.jar` 검증을 못하면 미검증 명시한다.
